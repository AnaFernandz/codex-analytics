How to use this guide

Generative AI quality assurance evaluates the complete product that uses a model, not whether one response sounds plausible. A dependable program combines conventional software testing with repeated, risk-based evaluation of probabilistic behavior, data, safety controls, integrations, and human outcomes.

Use the chapters as a lifecycle: define intended use and unacceptable outcomes; build a representative evaluation set; test components and end-to-end workflows; probe failure modes; set release gates; monitor production; and feed incidents back into the suite. The appendices provide reusable templates.

Core principle A passing average score does not establish safety. Set explicit, risk-weighted gates for severe failure modes, evaluate relevant slices, and retain human review where impact requires it.

1. Define what is under test

Draw the system boundary before writing test cases. Production behavior emerges from the model plus orchestration code, system instructions, retrieval index, connected tools, safety filters, UI, data permissions, and operational controls. A model-only benchmark misses failures at these boundaries.

1.1 Inventory the system

  • User journey: user groups, tasks, supported languages, channels, accessibility needs, and expertise.
  • Model configuration: provider and model version, prompts, decoding settings, output constraints, fallback and routing.
  • Knowledge path: sources, ingestion, chunking, embeddings, ranking, filters, freshness, citations, access controls.
  • Actions and tools: APIs, scopes, identity propagation, approval, side effects, retries, idempotency, rollback.
  • Controls: moderation, DLP, logging, retention, rate limits, incident response, human escalation, kill switches.
  • Changeable dependencies: model/provider, prompt, policy, index, embedding model, tool schema, safety classifier, application release.

1.2 Write testable requirements

Express requirements as observable outcomes with a population, context, measure, and threshold. “Be accurate” is not testable. “For in-scope support questions, answer with a correct policy grounded in the current approved source; when evidence is insufficient, abstain or escalate; never disclose unauthorized account data” can be evaluated.

ClassExample requirement
Task successComplete supported intents or state what information is missing.
FactualityMaterial claims are supported by retrieved evidence; unsupported claims trigger abstention.
SafetyRefuse disallowed assistance while answering benign adjacent requests.
PrivacyA user cannot retrieve another tenant’s records through prompting or memory.
ReliabilityTimeout, malformed output, tool failure, and provider outage result in safe recovery.
ExperienceMeet agreed latency, clarity, accessibility, tone, and handoff needs.

1.3 Establish a system card

Keep a living test-facing record of intended and excluded use, user groups, languages, known limitations, data sources, model and component versions, risk owners, safety policy, human oversight, and evaluation results. Record what the system cannot reliably do.

2. Build a risk-based test strategy

Risk determines test depth. A drafting aid needs different gates from a system that changes customer records, gives consequential advice, or influences access to services. Rate credible failures by severity, likelihood, exposure, and detectability; assign preventive controls and release evidence.

2.1 Risk assessment workflow

  1. Describe intended users, use, context, affected people, and plausible misuse.
  2. List harms and failure modes across model, data, application, integration, and operations.
  3. Estimate impact and exposure, including severity, reversibility, scale, vulnerable groups, and whether a human can intervene.
  4. Map each risk to a control, test method, acceptance criterion, and named owner.
  5. Review residual risk with accountable product, security, privacy, legal, and domain owners; record exceptions and expiry.
  6. Reassess after changes to model, prompt, data, tools, user population, policy, context, or after incidents.

2.2 Risk classes and test implications

RiskExample failureTypical evidence
Task / factualConfident wrong answerGold set, claim support, abstention, expert review
SafetyHarmful assistance or biasPolicy scenarios, red-team probes, subgroup review
SecurityInjection, data exposure, unsafe actionThreat model, penetration and authorization tests

Risk-based coverage Test frequency and independence rise with potential harm. High-impact uses need qualified domain experts, security specialists, affected-user perspectives where appropriate, and independent release review.

3. Design an evaluation set that represents use

A small demo set can hide real-world failures. Build a versioned suite from intended-use tasks, lawful support logs, expert-authored cases, incidents, and adversarial scenarios. Keep a holdout set so tuning does not overfit all visible examples.

3.1 Partition and tag examples

  • Smoke set: small stable suite for every change.
  • Regression set: representative historical failures and core journeys.
  • Challenge set: rare, adversarial, ambiguous, multilingual, long-context, and boundary cases.
  • Holdout set: controlled cases not used to tune prompts or policies; rotate carefully to reduce leakage.
  • Production sample: privacy-reviewed and minimized data sampled under approved retention and access rules.

Tag examples by intent, risk, language, user type, domain, difficulty, expected behavior, refusal/abstention, source/tool dependency, and failure severity. Evaluate slices because averages can hide concentrated harm.

3.3 Label with care

For open-ended tasks, define a rubric before seeing output. Use qualified reviewers for domain-sensitive claims; calibrate with examples, double-label a sample, measure agreement, adjudicate disagreement, and clarify ambiguous instructions. Model-based graders can scale triage, but validate their errors against human judgments. They should not be the sole authority for high-impact pass/fail decisions.

4. Measure quality without false precision

No single metric captures quality. Combine task outcomes, output quality, safety, system behavior, and human impact. Define numerator, denominator, sample method, uncertainty, slice, and threshold before interpreting results.

DimensionMeasuresCautions
Task completionSuccess rate; exact-match/schema validityMeasure user goal, not fluency.
Factual groundingClaim support; citation precision/recall; contradictionDefine material claims; citations can be irrelevant.
AbstentionAppropriate abstention; coverage; false abstentionReport coverage with quality.
SafetyViolation rate by severity; refusal precision/recallSeparate severe events and benign false refusals.
FairnessQuality/harm by relevant groups and languagesSmall samples need uncertainty and expert review.
RAGRecall@k, context precision, faithfulness, freshness, accessRetrieval and answer quality are distinct.
AgentsTool choice, argument validity, permissions, side effectsScore complete trajectories.
ReliabilityAvailability, p50/p95 latency, error, fallbackSegment by provider/route and degraded mode.
EconomicsCost per successful task, tokens, tool calls, retriesCheap failures are not efficient.

4.1 Layer the measures

  • Deterministic assertions for schemas, permissions, redaction, allowlists, and invariants.
  • Reference-based checks for facts, calculations, citations, and policy requirements.
  • Rubric review for relevance, completeness, clarity, tone, and support.
  • Human expert review for high-impact claims, nuanced safety, and disputed judgments.
  • Behavioral statistics across repeated runs for nondeterministic systems, with uncertainty.

Do not treat a judge score as objective truth. Validate graders on human-labeled samples, test position/style bias, and use pairwise comparisons where absolute scales are unstable. Freeze grader prompts and versions for comparisons; retain raw outputs and adjudication records.

5. Functional, conversational, and regression testing

5.1 Conventional tests still matter

Test the application like software: unit tests for prompt assembly and policy logic; contract tests for provider and tool schemas; integration tests for retrieval, identity, moderation, and persistence; end-to-end journeys; and resilience tests. Mock external calls for deterministic component tests, then run controlled live-model evaluations.

5.2 Conversation behaviors

  • Context: follow-up references, topic shifts, long histories, summaries, contradictions, and corrections.
  • Instruction hierarchy: attempts to override system constraints; quoted or retrieved instructions; conflicting requests.
  • Uncertainty: ambiguity, missing/stale data, conflicting sources, unsupported premises.
  • Output contract: language, format, length, tone, citations, schema validity, escaping, truncation.
  • Boundary behavior: benign requests near restricted content; refusal, safe alternatives, escalation.
  • State: memory persistence, deletion, cross-session isolation, consent, visible user controls.

5.3 Nondeterminism and reproducibility

Record exact inputs, conversation, model/provider ID, prompt and policy versions, decoding settings, retrieval snapshot, tool responses, timestamp, and evaluator version. Repeat cases at a defined rate and compare distributions or pass probabilities. A fixed seed helps only when the inference path honors it. Allow acceptable variation while keeping safety invariants strict.

6. RAG and knowledge-grounded systems

RAG quality is a chain: source quality and freshness → ingestion and chunking → retrieval and authorization → context selection → answer generation → citations and interpretation. Test each stage independently and end-to-end. A correct answer does not prove retrieved evidence was valid or authorized.

StageTest ideas
Source / ingestionMissing, duplicate, malformed, stale files; OCR errors; deletion; poisoned instructions
Chunking / embeddingsBoundary facts, tables, headings, multilingual queries, duplicates, tenant leakage
Retrieval / filtersKnown-answer recall, hard negatives, filters, ranking, freshness, permission changes
Context constructionToken budget, truncation, source diversity, malicious text, conflicting evidence
Answer / citationsClaim support, citation correctness, no invented citations, uncertainty on gaps
OperationsIndex rebuild/rollback, cache invalidation, outage, observability, deletion requests

6.1 Core RAG scenarios

  • Answerable query and one authoritative source; verify retrieval and citation.
  • Unanswerable query; state evidence is insufficient instead of inventing an answer.
  • Conflicting versions; choose approved current source or surface conflict.
  • Injection in a document; treat retrieved content as untrusted data.
  • Unauthorized document; test direct retrieval, paraphrase, memory, and cached results.
  • Deletion or permission revocation; verify disappearance within the documented window.
  • Adversarial query retrieves irrelevant chunks; ensure the answer does not confidently synthesize them.

7. Agents, tools, and multimodal systems

7.1 Agentic workflows

Agents can change external state. Define a bounded operating envelope: allowed tools, least-privilege identity, actions, per-step and total budgets, approvals, reversibility, and stop conditions. Test the entire trajectory: plan, tool selection, arguments, identity, returned data, next action, confirmation, and final report.

  • Authorization: propagate user identity and permissions; model-generated arguments never grant authority.
  • Injection: content from users, documents, email, web, or tool results cannot trigger unauthorized actions.
  • Action safety: payment, deletion, messaging, publishing, and account changes use required confirmation.
  • Bounds: step, token, spend, retry, recursion, time, and tool-scope limits stop loops safely.
  • Correctness: validate arguments/results, make duplicate actions idempotent, report tool failures honestly.
  • Recovery: handle timeout, partial completion, stale state, rate limits, compensation, and safe handoff.

7.2 Multimodal inputs and outputs

For image, audio, video, and generated media, test OCR/transcription errors, accents, overlapping speakers, timestamps, scene transitions, hidden/adversarial content, cross-modal contradictions, and missing metadata. Apply consent, retention, and access controls to derived transcripts, embeddings, thumbnails, and summaries too. Evaluate generated media for policy, prompt fidelity, artifacts, disclosure, and applicable labeling requirements.

8. Safety, security, privacy, and abuse testing

Run risk-based red-team testing against the deployed configuration. Include ordinary misuse, adversarial inputs, abuse at scale, and multi-turn attacks. Use isolated environments and synthetic data; do not probe production or third parties beyond authorized scope.

8.1 Security coverage

ThreatTest questions
Prompt injectionCan direct/indirect instructions override policy, expose secrets, or cause an action?
Sensitive informationCan prompts, outputs, logs, memory, retrieval, or errors disclose PII, secrets, or another tenant’s data?
Output handlingCan generated HTML, SQL, code, URLs, or structured data reach a sink without validation/encoding?
Excessive agencyCan the model use powerful tools, cross trust boundaries, or act without approval?
Prompt leakageCan disclosure expose sensitive operational details? Keep real secrets outside prompts.
Vector / embeddingCan poisoning, weak isolation, retrieval manipulation, or inversion expose/corrupt data?
Unbounded consumptionCan long context, retries, or recursion cause denial of service or runaway spend?
Supply chain / poisoningAre models, data, libraries, prompts, and indexes versioned, reviewed, and tamper-protected?

Use current OWASP GenAI materials as a threat checklist and map risks to local controls. OWASP identifies its 2026 Top 10 as the latest community guide at this edition date; the actual test plan must reflect the system threat model.

8.2 Safety and privacy scenarios

  • Jailbreaks/obfuscation: paraphrase, encoding, split requests, role-play, multilingual variants, multi-turn escalation.
  • Over-refusal: benign education, support, accessibility, or defensive tasks blocked by broad filters.
  • Policy harms: harassment, hate, self-harm, violence, sexual content, exploitation, consequential advice as applicable.
  • Privacy: extraction, secrets in context, memorization where relevant, logs, deletion, and isolation.
  • Fairness: differential quality, refusal, toxicity, or escalation across relevant groups, dialects, languages, accessibility.
  • Oversight: users recognize uncertainty, correct errors, appeal, contact a human, and understand consequential actions.
Interpretation A prompt-only jailbreak suite is not a complete security assessment. Combine behavior probes with authorization, data-flow, output-sink, infrastructure, and operations tests.

9. Test execution and CI/CD

Make evaluation repeatable and proportionate. Fast deterministic checks run on every change; model suites run on material prompt, model, data, policy, or tool changes; broader adversarial and expert evaluation runs before launch and periodically. Keep production credentials and sensitive datasets out of ordinary CI.

9.1 Suggested test layers

LayerWhenExamples
Static / unitEvery commitPrompt assembly, schema, escaping, policy, allowlist, invariants
Contract / integrationEvery buildProvider shape, retrieval, identity filters, moderation, tool contracts
Smoke evalEvery deploy candidateCritical safety cases, core journeys, latency and fallback
Regression evalMaterial changesRepresentative corpus, slices, repeated runs, grader and human sample
Red team / expertLaunch; material change; scheduleThreat scenarios, harms, agent trajectories, domain review
Production canaryControlled rolloutLimited traffic, quality, latency, cost, errors, user feedback

9.2 Release gates

  • All critical deterministic tests pass: authorization, isolation, tool limits, schema, redaction, fallback.
  • No unresolved critical/high failure without documented, time-bounded risk acceptance by authorized owner.
  • Quality and safety thresholds are met overall and by required risk slices; sample and uncertainty are adequate.
  • Regressions from approved baseline are explained; comparisons hold config/evaluator versions constant.
  • Operational readiness: limits, budgets, alerts, rollback, escalation, support owner, incident runbook.
  • Evidence records build/model IDs, prompt/policy hashes, data/index version, results, reviewer, decision.

9.3 Change impact matrix

10. Production monitoring and incident learning

Evaluation continues after launch. Monitor product and system signals under approved privacy and retention rules. Prefer aggregate metrics and minimized samples. Log enough to reconstruct failures—versions, route, tool trace, citations, timing, token/cost counts, outcome—while protecting sensitive content.

10.1 Leading indicators

  • Operational: availability, p50/p95 latency, timeout/retry, fallback, queue depth, provider errors.
  • Quality: task completion, user correction/retry, citation errors, abstention, unresolved intents, expert sample.
  • Safety/security: policy violations, injection indicators, unauthorized tool attempts, access anomalies, near misses.
  • Cost: spend per successful task, tokens, tool-call depth, unusual usage, rate limits.
  • Drift: input mix, languages, topics, retrieval coverage, refusals, feedback and outcomes.

10.2 Incident response loop

  1. Contain: disable risky tool/route, tighten access, switch model, turn off feature, or roll back.
  2. Preserve relevant evidence safely: request, output, tool trace, versions, timestamps, controlled logs.
  3. Triage users, duration, severity, exploitability, data exposure, downstream actions, and obligations.
  4. Remediate and retest the exact issue plus nearby variants; one reproduction passing is not enough.
  5. Update regression suite, register, controls, runbook, stakeholder communication; monitor recurrence.

11. Team operating model and evidence

QA is shared work with clear decision ownership. Product defines intended use; engineering implements and instruments; QA owns evaluation design and evidence; security probes attack surfaces; data teams own lineage/access; domain experts judge specialized claims; privacy/legal/risk advise obligations; operations own monitoring and response. Roles may combine, but decisions and evidence remain explicit.

Reference points include NIST AI RMF and its Generative AI Profile for lifecycle risk management, OWASP GenAI security materials for application threats, and ISO/IEC 42001 for organizational AI management. They inform governance and test planning; they do not replace product criteria or applicable legal review.

Worked example: internal policy assistant

Suppose employees ask questions about travel and expense policy. The assistant searches approved internal documents and cites the source. The most useful first suite tests the evidence path, access boundaries, uncertainty, and failure recovery together.

ScenarioInput / setupExpected resultEvidence to capture
Current policy answerAsk the reimbursement limit; current policy is indexed.Gives the correct limit and cites the current approved policy section.Retrieved document ID/version, answer claims, citation target.
Missing evidenceAsk about an exception absent from the source set.Says the policy does not establish the answer and routes to the policy owner.Top retrieved results, abstention label, handoff outcome.
Stale policyKeep an old and new policy version in the test index.Uses the approved current version or clearly surfaces a conflict.Version metadata, ranking, freshness and answer trace.

A compact acceptance rule

Release only when every authorization and severe-safety invariant passes, citations resolve to the expected approved source, unsupported questions abstain as designed, and the outage path does not fabricate an answer. Track ordinary answer quality separately from these zero-tolerance checks.

Starter checklist for your first evaluation run

  1. Choose one user journey and write its success condition in observable terms.
  2. List five ordinary examples, five edge cases, and five high-risk or adversarial cases.
  3. Mark expected answer, refusal, abstention, clarification, or human handoff for each case.
  4. Record exact model, prompt, data/index, policy, tool, and evaluator versions.
  5. Run each case, capture output and traces, score against a fixed rubric, and triage every severe failure.
  6. Turn every confirmed failure into a regression case and assign an owner and retest date.
